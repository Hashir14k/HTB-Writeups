Synopsis

VVM is a hard reverse engineering challenge featuring a custom stack-based virtual machine (Very Virtual Machine v0.0.3) that implements a password-checking bytecode program. The binary employs anti-debugging via ptrace, encrypted code handlers, and a multi-level bytecode interpreter with nested sub-bytecode dispatch loops.

Goal Reverse engineer the custom VM architecture, extract the 32-character flag by recovering the expected packed comparison values, inverting the per-group ROTL transformation, and descrambling the character permutation.

The challenge requires:

  • Patching the ptrace anti-debugging check
  • Dumping all 28 VM opcode handlers via GDB + QEMU-user
  • Decoding the bytecode program and sub-bytecodes
  • Recovering expected packed values and reversing the ROTL transformation
  • Descrambling the flag character permutation order

Bypassing Anti-Debugging

The ptrace call at 0x13f2 calls PTRACE_TRACEME. The return value is tested at 0x13f7: if negative (debugger attached), the program calls exit(1). Patching the js conditional to nop; nop at file offset 0x13fa bypasses the check: 

# Python: patch ptrace check
with open('vvm', 'r+b') as f:
    f.seek(0x13fa)
    f.write(bytes([0x90, 0x90]))  # js 0x1401 → nop; nop

After patching, the binary reveals the full prompt:

=======================

=======================

VM Architecture Discovery

Using x86_64-linux-gnu-objdump to disassemble the binary reveals three key functions called from main:

  1. Function 0x2910 — Prints the banner (=====\nvvm v0.0.3\n=====)
  2. Function 0x1530 — VM initialization: allocates the VM state (0xe0 bytes), decrypts 24 code chunks into executable memory via mmap, and populates the opcode handler table
  3. Function 0x2870 — VM execution loop: reads 32-bit opcodes from bytecode at 0x5540, dispatches via call [r8 + opcode*8], halts on opcode 28
Key Discovery The VM dispatch at 0x28d8 calls [r8 + r9*8] where r8 is the VM state base (stored at VA 0x74e0) and r9 is the opcode. Each handler is an 8-byte function pointer — 28 handlers total (opcodes 0–27).

Solution

Dumping Opcode Handlers via GDB + QEMU

Since the system is ARM64 but the binary is x86-64, we use qemu-x86_64 with GDB stub (-g PORT) and connect with gdb-multiarch. By breaking at the execution loop entry (0x555555558870), we can read the VM state pointer and dump all 28 handler addresses: 

# GDB: dump handler table
set $vmstate_ptr = *(long long*)0x55555555d4e0
set $i = 0
while $i < 28
  set $handler = *(long long*)($vmstate_ptr + $i * 8)
  if $handler != 0
    printf "opcode %2d: handler at %p\n", $i, $handler
    x/30i $handler
  end
  set $i = $i + 1
end

Understanding the Bytecode Program

The bytecode at 0x5540 implements three phases:

Phase 1: Prompt String Computation

The prompt "What is the password: " is not decrypted from a string table — it is computed character-by-character using arithmetic operations on PUSH'd immediate values: 

# Example: computing 'W' (87)
PUSH 174
PUSH 2
DIV          # 174/2 = 87 = 'W'

# Computing 'a' (97)
PUSH 52
PUSH 2
MUL          # 104
DUP
PUSH 7
SUB          # 104-7 = 97 = 'a'

After computing all 22 prompt characters, the ARRAY opcode packs them for printing.

Phase 2: Input Reading & Length Check

GETLINE reads the password. STRLEN computes its length N, which is transformed through: (N×6 - 8) ÷ 2 × 8 + 24 ÷ 10. For N=32, this yields 76. The expected length-derived value is also 76, confirming the flag is 32 characters.

Phase 3: Character Scrambling & Group Packing

The 32 flag characters are read in scrambled order via 32 GET_CHAR operations, organized into 8 groups of 4:

OR          # packed = byte0 | (byte1<<8) | (byte2<<16) | (byte3<<24)

The ROTL Transformation

Each packed group is transformed by sub-bytecode 456 before comparison. Analysis of sub-bytecode 456 reveals it computes: 

# Sub-bytecode 456: ROTL(packed, setup)
PEEK 1      # push setup value
PEEK 1      # push packed value
SHL         # packed << setup
PEEK 2      # push packed again
PUSH 32
PEEK 3      # push setup again
SUB         # 32 - setup
SHR         # packed >> (32 - setup)
OR          # result = ROTL(packed, setup)
HALT

Verified with all-'A' (0x41414141) input:

# Python verification
def rotl32(x, n):
    return ((x << n) | (x >> (32 - n))) & 0xFFFFFFFF

assert rotl32(0x41414141, 15) == 0xA0A0A0A0  # ✓ matches gdb trace!

Critical Insight The transformation order is REVERSE of the packing order. The last-packed group (group 7) is transformed first (setup=15), while the first-packed group (group 0) is transformed last (setup=7).

Full Solver Script

#!/usr/bin/env python3
"""VVM Flag Solver — HTB Reverse Engineering Challenge"""
import struct

def rotl32(x, n):
    return ((x << (n & 0x1F)) | (x >> (32 - (n & 0x1F)))) & 0xFFFFFFFF

def rotr32(x, n):
    return rotl32(x, 32 - (n & 0x1F))

# Expected transformed values from bytecode PUSHes at pc=555-592
expected = [
    706975780,   # 0x2A222224
    2322852449,  # 0x8A720A61
    3124542873,  # 0xBA3C3C99
    3720205581,  # 0xDDDDB50D
    4081337093,  # 0xF3474345
    1193747491,  # 0x47272423
    353885596,   # 0x1517DD9C
    3057234985,  # 0xB639B429
]

# Setup values (ROTL rotation amounts)
setups = [15, 19, 7, 18, 12, 20, 14, 7]

# GET_CHAR position groups
groups = [
    [24, 14, 27, 15], [11, 7, 12, 4],
    [6, 9, 2, 18], [19, 13, 20, 26],
    [28, 16, 23, 8], [3, 30, 21, 22],
    [25, 5, 10, 31], [29, 1, 0, 17],
]

# Map transform order → group (reversed!)
setup_to_group = [7, 6, 5, 4, 3, 2, 1, 0]

flag = ['?'] * 32
for si, gi in enumerate(setup_to_group):
    packed = rotr32(expected[si], setups[si])
    for byte_i, flag_pos in enumerate(groups[gi]):
        flag[flag_pos] = chr((packed >> (byte_i * 8)) & 0xFF)

print(''.join(flag))
# Output: HTB{v1rTu4L_p4sSw0rD_t3ChN0loGy}

Attack Flow Summary

  1. Patch anti-debugging — NOP the js after ptrace at file offset 0x13fa
  2. Disassemble the binary — Use x86_64-linux-gnu-objdump to identify main, VM init, and VM exec loop
  3. Dump handler table — Use GDB + QEMU-user to capture all 28 opcode handler function pointers and disassemble each one
  4. Identify all opcodes — Analyze each handler to build the complete VM ISA (ADD, SUB, MUL, DIV, PUSH, PEEK, LOOP, EQ, COND_JMP, etc.)
  5. Trace bytecode execution — Emulate the bytecode program to understand prompt computation, length check, and flag validation flow
  6. Analyze sub-bytecodes — Decode sub-282 (packing) and sub-456 (ROTL transformation) called via the LOOP construct
  7. Extract expected values — Read the 8 PUSH constants at bytecode pc=555-592 and the 8 setup values (15, 19, 7, 18, 12, 20, 14, 7)
  8. Reverse ROTL — Compute ROTR(expected, setup) to recover the packed flag bytes for each group
  9. Descramble positions — Map packed bytes to flag positions using GET_CHAR indices, accounting for the reverse processing order
  10. Recover flag — Assemble the 32-character flag and verify against the original binary
