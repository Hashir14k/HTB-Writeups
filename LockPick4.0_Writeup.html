Scenario

Forela.org's IT Helpdesk has been receiving reports from employees experiencing
unusual behaviour on their Windows systems. Within 30 minutes, the number of
affected systems increased drastically, with employees unable to access their
files or run essential business applications. An ominous ransom note appeared
on many screens, asking the users to communicate with the ransomware group's
customer service department. It became apparent that Forela.org was under a
significant ransomware attack.

As a member of Forela.org's Incident Response (IR) team, you have been assigned
a critical task: reverse engineer the ransomware and extract Indicators of
Compromise (IOCs) to feed into the organisation's detection tools.

02

Executive Summary

LockPick is a JavaScript-driven ransomware delivered as a booby-trapped defenderscan.js with its real weapons hidden in NTFS alternate data streams. The dropper writes a lure image, executes an embedded PowerShell stage that abuses cmstp.exe to bypass UAC, disables Defender with Add-MpPreference exclusions, and then re-materialises the two stream-hidden executables as msmpeng.exe + mpsvc.dll.

The loader is a genuine, Microsoft-signed Windows Defender binary (MsMpEng.exe, 4.8.10240.16384). It imports one function from mpsvc.dll — ServiceCrtMain — so launching it executes the attacker's DLL through classic DLL search-order hijacking (T1574.001), no injection required.

The ransomware core decrypts an AES-256-CBC config from its own resource section (target folders, 10 target extensions, the ransom-note HTML), beacons its per-victim encryption passphrase plus the hostname to api.ltchealthcare.co:5000/connect over WinHTTP, AES-encrypts matching files, renames them with a .evil suffix, drops note.html, and displays it full-screen via msedge.exe. Victims are directed to a Tor customer-service portal operated by the RedBadger group.

TL;DR — a staged JScript/ADS dropper, a CMSTP UAC bypass, a signed-binary DLL hijack, and an AES ransomware core with config, C2 beacon, .evil renames, and an onion support desk. Ten questions below cover every observable IOC.
03

Initial Analysis

First step was extracting the disk image and fingerprinting everything inside it — with the surprise hiding in the NTFS metadata.

Unpacking the VHDX

7-Zip reads VHDX directly: the image holds a GPT partition table and a single NTFS 3.1 volume. Extracting it surfaced three user-visible items — a lure ReadMe.txt, the 128 KB defenderscan.js, and, crucially, two NTFS alternate data streams attached to the JS file:

$ 7z l defenderscan.vhdx
Path = 0.Basic data partition.ntfs
File System = NTFS 3.1            Label = New Volume
Alternate Streams: 6

$ file defenderscan.js*
defenderscan.js:          ASCII text, with very long lines (58130), CRLF
defenderscan.js:payload:  PE32+ executable (DLL) x86-64, 6 sections
defenderscan.js:lolbin:   PE32+ executable (GUI) x86-64, 6 sections

The ReadMe.txt is pure social engineering: a fake "IT Security Team" notice instructing employees to run defenderscan.js for a "security verification". The ADS pair is the weaponry: a signed GUI executable (:lolbin) and a DLL (:payload). The loader's version resources identify it as the real Antimalware Service Executable (MsMpEng.exe, Windows 10 TH1 build), code-signed by Microsoft Corporation — a textbook side-loading vehicle.

ADS as stealth: streams hidden on a .js file survive most AV on-access scans and simple file copies, and the dropper later reads them back by their stream names — defenderscan.js:lolbin / defenderscan.js:payload (base64 in the PowerShell stage). MITRE: T1564.004.
04

The Attack Chain

Five stages take the sample from a double-clicked script to encrypted files and a full-screen ransom note. Arrows carry the artifact that moves between stages.

Stage 1 — defenderscan.js (the dropper)

The script is lightly obfuscated: two base64 blobs (b64img, b64s) and helper functions. Its first observable action is writing a 89,292-byte WEBP image — redbadger.webp — to the working directory. It then decodes b64s into a PowerShell script, saves it under a random temp name, runs it with -ExecutionPolicy Bypass, and deletes the file:

// defenderscan.js (deobfuscated flow)
var f = new ActiveXObject("Scripting.FileSystemObject");
// 1. FIRST write to disk — the RedBadger badge used by the ransom note
var binData = b642str(b64img);
var fname   = "redbadger.webp";
bin2file(binData, fname);                     // ADODB.Stream → SaveToFile
// 2. decode embedded PowerShell (b64s) → temp file → Invoke-Expression
var cmd = "powershell.exe -ExecutionPolicy Bypass -Command \"& { " +
          "$scrContent = Get-Content -Path '" + tmpFilePath + "' -Raw; " +
          "Invoke-Expression $scrContent }\"" ;
sh.Run(cmd, 0, true);
f.DeleteFile(tmpFilePath);

Stage 2 — the PowerShell stage

Decoded from b64s (5,498 bytes; SHA-256 a1ef73ce…65762db4), this stage is a Lord-of-the-Rings-themed privilege escalation and drop routine:

  • Privilege check — Test-HobbitInCouncil runs whoami /groups and matches the local Administrators SID S-1-5-32-544 (and Domain Admins). Non-admins get nothing.
  • UAC bypass — if a local admin but not elevated, Bypass-GondorGate writes %temp%\ScrollOfEru.inf, runs cmstp.exe /au ScrollOfEru.inf, and auto-approves the UAC prompt with SendKeys {ENTER}. The INF's RunPreSetupCommands re-launches wscript.exe elevated, then taskkill /IM cmstp.exe /F.
  • Defender disarm — Add-MpPreference -ExclusionProcess msmpeng.exe and -ExclusionPath for the working directory.
  • Payload drop — reads the ADS pair and writes msmpeng.exe (:lolbin) and mpsvc.dll (:payload), starts the EXE, then deletes both files.

Stage 3 — the signed loader

:lolbin is not attacker code: its version resources say MsMpEng.exe, Antimalware Service Executable, 4.8.10240.16384, and its Authenticode chain is production Microsoft (CN=Microsoft Corporation, OU=MOPR under Microsoft Code Signing PCA). Its import table contains exactly one DLL dependency of interest:

msmpeng.exe  →  mpsvc.dll :: ServiceCrtMain

Because Windows resolves a binary's own directory first, the attacker's mpsvc.dll sits beside the copied MsMpEng.exe and wins. Launching the "Defender binary" executes the ransomware — T1574.001, DLL search-order hijacking.

Stage 4 — mpsvc.dll, the ransomware core

The DLL exports one function — ServiceCrtMain — which the loader calls directly. Inside, before any malicious behavior, three anti-analysis gates run (details in Q6). Then:

  1. Config — resource #101 (2,464 bytes) is decrypted with AES-256-CBC (key and IV embedded in the resource) into a JSON config: 6 userFolders, 10 fileExtensions, and the ransom-note HTML (html_content).
  2. C2 beacon — an HTTPComms object POSTs to https://api.ltchealthcare.co:5000/connect with {"passphrase":"…","hostname":"<computername>"} — the per-victim encryption key leaves the host before any file is touched (T1041).
  3. Encryption — FindFirstFileW walks the six folders; files whose extension matches the config list are AES-encrypted via bcrypt, written back, then renamed with MoveFileExW(orig, orig+".evil", REPLACE_EXISTING|COPY_ALLOWED).
  4. Ransom note — note.html is dropped and opened via ShellExecuteA("msedge.exe", "note.html --start-fullscreen") after system("taskkill /F /IM msedge.exe").
05

Under the Hood — Obfuscation & Crypto

The sample's most instructive engineering is its string protection: a SIMD-accelerated repeating-XOR cipher, and an AES config blob that hides the entire ransom-note payload.

Obfuscated strings: a SIMD repeating-XOR

Six 21-byte globals (all materialising the C2 hostname) are decrypted at first use by a vectorised routine that is an optimised form of a repeating 8-byte XOR. The scalar fallback inside the same function makes the scheme explicit:

; fcn.180003500 — tail loop (scalar path) — r8 = key, r9 = len, r10 = buf
0x180003670: movzx ecx, al      ; j = index
             and   cl, 7        ; j & 7
             shl   cl, 3
             shr   rdx, cl      ; key >> (j&7)*8
             xor   [r10+rax], dl   ; buf[j] ^= key[j%8]
             inc   rax          ; j++
             cmp   rax, r9 / jb

The SIMD path reproduces the same stream with vector constants: paddq {0,1}, andps {7,7}, pshufb {0x00,0x08,0x00,…} over a duplicated 64-bit key — a nice reminder that modern obfuscators lean on SSE for string ciphers. Recovering the stream needed only the 8-byte key and index alignment:

# C2 FQDN — ct = 21 bytes, key = 0x91219B1FF7F5F1D5 (LE)
ct = b4 81 9c d9 73 ef 42 f9 b0 90 99 83 77 f8 40 e3 b0 df 96 98 1f
key = d5 f1 f5 f7 1f 9b 21 91
pt  = api.ltchealthcare.co\x00

# rename suffix — fcn.180004f80, key = 0x656173452549D30D
ct = 23 b6 3f 4c 29 73 01
pt  = .evil\x00

Config: AES-256-CBC in the resource section

Resource #101 (RT_RCDATA, 2,464 bytes) is not parsed directly — FindResourceW/LoadResource/LockResource feed it to BCryptDecrypt with the layout key(32) ‖ IV(16) ‖ ciphertext (AES-256-CBC, PKCS#7). The plaintext is the entire operational configuration:

{
  "userFolders": ["%USERPROFILE%\\Desktop","%USERPROFILE%\\Documents",
    "%USERPROFILE%\\Downloads","%USERPROFILE%\\Music",
    "%USERPROFILE%\\Pictures","%USERPROFILE%\\Videos"],
  "fileExtensions": [".doc",".docx",".xls",".xlsx",".ppt",
    ".pptx",".pdf",".txt",".csv",".rtf"],
  "html_content": "PCFET0NUWVBFIGh0bWw+…"      // base64 of note.html
}

This is why the C2 hostname never appears in the file's plain strings: the FQDN is XOR-obfuscated in code, and the note HTML is ciphertext in the resource section. Two different protections, both defeated statically — no sandbox needed.

Questions & Answers

All eleven challenge questions, with the evidence trail that produced each answer.

Q1What is the MD5 hash of the first file the ransomware writes to disk?
2c92c3905a8b978787e83632739f7071

The first write of the whole package is redbadger.webp — decoded from the dropper's b64img blob and saved via ADODB.Stream.SaveToFile before anything else. Confirmed non-decoys: the DLL's own first writes are dynamic encrypted files (unhashable by design), and note.html is written after encryption — while the webp is referenced twice by that very note. SHA-256: 9ee911d2…434adf88.

Q2What is the string the ransomware uses to check for local administrator privileges?
S-1-5-32-544

Test-HobbitInCouncil runs whoami /groups and regex-matches the output for the well-known SID of the local Administrators group. The check only appears in the PowerShell stage — neither the JS nor the DLL contains SID strings.

Q3What is the MITRE ATT&CK ID for the technique used by the threat actor to elevate their privileges?
T1218.003

Bypass-GondorGate writes ScrollOfEru.inf and runs cmstp.exe /au — an auto-elevated signed binary — whose RunPreSetupCommands re-launches the dropper elevated; SendKeys {ENTER} approves the UAC prompt. That is the classic CMSTP UAC-bypass (parent: T1548.002).

Q4The ransomware starts a process using a signed binary, what is the full name of the signer?
Microsoft Corporation

The dropped msmpeng.exe is the genuine Antimalware Service Executable (4.8.10240.16384) with a production Authenticode chain: CN=Microsoft Corporation, OU=MOPR, O=Microsoft Corporation under Microsoft Code Signing PCA. The DLL also launches msedge.exe — likewise Microsoft-signed. Either path answers the question the same way.

Q5What is the final payload's entry point function?
ServiceCrtMain

mpsvc.dll exports exactly one symbol — ServiceCrtMain — and the loader imports exactly that one symbol from it. The PE's raw AddressOfEntryPoint is just the compiler's CRT stub; the malware logic begins in the exported function.

Q6How many Anti-Debugging techniques does the ransomware implement and what is the Windows API function that the final technique leverages?
3, SetUnhandledExceptionFilter

Three gates open ServiceCrtMain: (1) IsDebuggerPresent → bail; (2) a CreateToolhelp32Snapshot walk requiring its own PID to appear, with a second pass comparing entry names against powershell.exe → exit(0) on mismatch; (3) the final trap — re-registering the current handler with SetUnhandledExceptionFilter then raising INT3, which behaves differently under a debugger. (The CRT's own crash-reporter also calls IsDebuggerPresent; that is compiler boilerplate, not a fourth check.)

Q7What is the list of extensions targeted, in the exact order the configuration stores them?
.doc, .docx, .xls, .xlsx, .ppt, .pptx, .pdf, .txt, .csv, .rtf

Straight from the decrypted resource #101 JSON — the fileExtensions array, in storage order. Office formats, PDF, and plain text across the six %USERPROFILE% folders.

Q8What is the FQDN of the ransomware server the malware connects to?
api.ltchealthcare.co

Hidden in a 21-byte XOR blob decrypted at runtime (0x91219b1ff7f5f1d5) and passed to WinHttpConnect(handle, fqdn, 0x1388) — port 5000 — with POST /connect and UA A WinHTTP Example Program/1.0. Six duplicated magic-statics all decrypt to the same hostname.

Q9What is the full URL including port number of the ransomware group's customer service portal?
yrwm7tdvrtejpx7ogfhax2xuxkqejp2qjb634qwwyoyabkt2eydssrad.onion:9001

From the decrypted note.html: victims browse to the onion over Tor to talk to the RedBadger "customer service department". Note the clean split: machine-to-machine C2 at api.ltchealthcare.co:5000, humans at the onion:9001.

Q10What is the file extension used to store the newly encrypted files?
.evil

After AES encryption, fcn.180004080 appends a runtime-decrypted global and calls MoveFileExW(orig, orig+ext, REPLACE_EXISTING|COPY_ALLOWED). The global is decoded by fcn.180004f80 (XOR key 0d d3 49 25 45 73 61 65, whose high bytes spell "Esea"): report.doc becomes report.doc.evil.

Q11What is the MITRE ATT&CK ID the ransomware uses to run its final payload?
T1574.001

The final payload never runs on its own: planting mpsvc.dll where MsMpEng.exe resolves its only import hijacks the DLL search order. T1574.001 — Hijack Execution Flow: DLL Search Order Hijacking.

Static — YARA

    $pdb     = "ransomsvc\\WindowsClient\\x64\\Release\\mpsvc.pdb" nocase ascii
    $cfg1    = "fileExtensions" ascii

Dynamic — host & network telemetry

  • Process lineage: wscript.exe → powershell.exe -ExecutionPolicy Bypass; and any msmpeng.exe whose image path is not under %ProgramFiles%\Windows Defender\.
  • UAC bypass: cmstp.exe invoked with /au pointing at an INF under %temp%; INF containing RunPreSetupCommands.
  • Defender tamper: PowerShell Add-MpPreference with -ExclusionProcess/-ExclusionPath.
  • ADS abuse: file-create events for msmpeng.exe / mpsvc.dll in user-writable directories, and NTFS stream reads on .js files.
  • Network: outbound WinHTTP POST to api.ltchealthcare.co:5000/connect with the UA string above; DNS queries for the FQDN; Tor gateway traffic to the onion:9001.
  • Impact: volume-level MoveFileExW renames landing on *.evil; note.html creations; msedge.exe launched with --start-fullscreen right after taskkill /F /IM msedge.exe.

Appendix — Method & Tooling

Everything was produced with static analysis on an aarch64 Linux workstation — no sample code was executed:

  • Disk: 7-Zip for the VHDX→NTFS extraction (alternate streams recovered by name).
  • PE analysis: pefile (sections, imports/exports, resources, version info, Authenticode extraction), radare2 (disassembly, xrefs), strings, openssl (PKCS#7 parsing).
  • Deobfuscation: base64 blobs decoded from the JS; the SIMD XOR routine re-implemented in Python after recovering the vector constants (paddq {0,1}, andps {7,7}, pshufb {0x00,0x08,…}); the config decrypted with AES-256-CBC from the embedded key/IV/CT layout.
  • Lesson logged: r2's flat VA→file-offset view and pefile's memory-map indexing disagreed until verified against raw file bytes — the winning constants were the ones matching a decryptable FQDN. Trust the plaintext round-trip.
